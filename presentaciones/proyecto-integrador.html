Una API pequeña, un producto real

Dos entidades, una SPA y cuatro hitos. Sin funciones extra: lo que importa es que el producto funcione, esté seguro y puedan demostrarlo.

01Alcance

2 entidades relacionadas + usuario. 8–10 endpoints. Una sola página web.

02Equipo

Equipos de 2. Ambos programan, ambos explican, ambos defienden.

03Resultado

Una API con auth, base de datos, pruebas y una SPA que la consume.

Regla de oro: si una funcionalidad no está en la guía, no entra al proyecto.

Lo que debe funcionar

  • Registro e inicio de sesión.
  • Crear, listar y eliminar lo propio.
  • Un admin ve todo; un usuario no ve lo ajeno.
  • Errores 401, 403, 404 y 422 claros.
  • Pruebas en verde y demo reproducible.
Catálogo

Elijan un dominio (y solo uno)

Todos tienen una relación 1:N, reglas de negocio y un filtro. No se puede usar el dominio de los laboratorios.

ATablero → Tarea

Estados, prioridad y fecha límite.

Útil para organización personal.
BEspacio → Reserva

Inicio, fin y choques de horario.

Útil para reservar aulas o canchas.
CCategoría → Gasto

Monto, fecha y total del mes.

Útil para controlar gastos.
Una decisión por equipo: el dominio se registra en la propuesta de la sesión 4 y no se cambia después del Hito 1.

Reglas y evaluación

Qué se vale y qué no

Sí

  • FastAPI o PHP 8 con aprobación.
  • SQLite o PostgreSQL.
  • HTML, CSS y JavaScript vanilla.
  • IA como copiloto, con auditoría.
  • Dockerfile y demo en Codespaces/Render.

No

  • React, Vue o Angular.
  • Pagos, chat, tiempo real o IA en el producto.
  • Tercera entidad o funciones extra.
  • Copiar el dominio o el código de los laboratorios.
  • Secretos o contraseñas en el repositorio.
Evaluación por hito: 40% funcionalidad · 20% seguridad · 20% pruebas · 10% documentación · 10% demo. La nota individual se ajusta con commits y defensa.
